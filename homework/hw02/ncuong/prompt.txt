# Prompt kiểm thử Domain/EP + BVA cho một feature HW02

## Cấu hình duy nhất cần đổi

TARGET_FEATURE_ID: FR17

Đổi giá trị TARGET_FEATURE_ID khi chuyển feature. Tự tìm tên, rule, interface, test data và đường dẫn artifact từ repository; không sao chép kết quả của feature khác. Nếu ID không tồn tại hoặc trùng nhiều định nghĩa, ghi rõ vấn đề và dừng phần phụ thuộc vào việc xác định feature.

## Nhiệm vụ

Bạn là agent kiểm thử phần mềm. Thực hiện trọn quy trình Domain Testing bằng Equivalence Partitioning (EP) và Boundary Value Analysis (BVA) cho feature mục tiêu: đọc yêu cầu, thiết kế ca, chạy các ca khả thi trên SUT an toàn, lưu evidence, đánh giá coverage, báo cáo phát hiện và lập AI Audit Report. Không sửa source code gốc để làm test pass.

## Bước khởi đầu bắt buộc — trước khi đọc skills hoặc source code

Thực hiện đúng thứ tự sau từ thư mục gốc repository, cho mọi TARGET_FEATURE_ID:

1. Đọc đủ cả ba file: `README.md` ở gốc repo (rule nghiệp vụ và Expected), `api_specification.md` ở gốc repo (hợp đồng API), rồi `homework/hw02/docs/2026.HW02.Domain Testing_En.md` (phạm vi, phương pháp và đầu ra HW02). Đọc API spec ngay cả khi feature sau đó được thực thi qua UI hoặc mobile.
2. Quét cấu trúc repo ở mức tổng quan (ví dụ `rg --files`): nhận diện thư mục ứng dụng, tài liệu, feature mục tiêu, interface, test setup và artifact hiện có. Ở bước này chưa đi sâu vào implementation/source code hay chạy SUT.
3. Từ ba tài liệu và bản đồ repo, xác định mục/rule liên quan đến feature, nguồn Expected và chỗ thiếu hoặc mâu thuẫn. `README.md` gốc là nguồn rule nghiệp vụ; `api_specification.md` mô tả hợp đồng API; đề HW02 quyết định phạm vi và đầu ra. Nếu hai nguồn mâu thuẫn, ghi `UNRESOLVED` và tác động đến oracle, không tự chọn theo hành vi code.
4. Sau đó mới đọc README và các SKILL.md trong bộ skills, rồi kiểm tra source liên quan để chuẩn bị thực thi hoặc điều tra nguyên nhân. Không lấy hành vi SUT làm yêu cầu.

Nếu thiếu hoặc không đọc được một trong ba file bắt buộc, báo rõ file và dừng phần phụ thuộc vào tài liệu đó; không bịa rule hay Expected.

1. Sau bước khởi đầu ở trên, đọc `homework/hw02/ncuong/skills/README.md` và `domain-testing-workflow/SKILL.md` trước các skill chuyên biệt.

Decision table và state model chỉ hỗ trợ hiểu rule/setup khi cần. Bộ ca và coverage chính của HW02 vẫn là EP và BVA; không tự mở thêm bộ ca UI Validation hay coverage kỹ thuật thứ ba.

## Xác định phạm vi feature

- Chuẩn hóa TARGET_FEATURE_ID về mã requirement trong đặc tả (ví dụ FR02 tương ứng FR-02); giữ tên feature đúng nguồn.
- Xác định pool, actor, input, trạng thái trước, side effect, cả đường API lẫn UI/mobile có thật (nếu có), và dependencies tối thiểu cho setup.
- Chỉ kiểm thử rule của feature mục tiêu. Dùng feature khác để tạo fixture hoặc đăng nhập khi cần, nhưng không biến dependency thành bộ test mới.
- Phân loại rule CONFIRMED, ASSUMED hoặc UNRESOLVED. Ghi câu hỏi còn mở và các oracle bị ảnh hưởng. Không tự đặt threshold, status code, thông báo lỗi hay thứ tự ưu tiên rule.
- Giữ ID của artifact hiện có thuộc feature mục tiêu nếu đang tiếp tục một lần làm hợp lệ; khi bắt đầu lại từ đầu, không lấy số liệu hoặc evidence của run cũ làm kết quả mới.

## Thiết kế Domain/EP và BVA

1. Dùng input-domain-partitioner để xác định kiểu, miền, constraint, trạng thái và tổ hợp khả thi.
2. Dùng equivalence-partitioning-generator để tạo các lớp hành vi khác nhau; chọn giá trị đại diện cụ thể, giữ các chiều không liên quan ở baseline hợp lệ.
3. Dùng boundary-value-generator cho các ngưỡng, khoảng, độ dài, thời điểm hoặc quan hệ có ý nghĩa. Ghi dấu bằng thuộc phía nào, đơn vị, bước/độ chính xác và Expected tại từng điểm. Dùng ON/IN/OUT khi nhãn đó rõ ràng; với ngưỡng đổi hành vi, có thể ghi ngay dưới / tại biên / ngay trên. Không ép ±1 cho miền liên tục hoặc tạo điểm không thể biểu diễn.
4. Dùng test-oracle-writer để xác định Expected quan sát được từ đặc tả. Điểm thiếu oracle là Quan sát/INCONCLUSIVE, không tự chấm PASS/FAIL.
5. Dùng test-case-catalog cho một danh sách T-ID duy nhất. Một ca phục vụ cả EP và BVA chỉ xuất hiện một lần, giữ đủ liên kết P-ID/B-ID. Không tạo case chỉ để tăng số lượng.
6. Dùng coverage-goal-planner: nêu mẫu số là các lớp EP và điểm BVA đủ điều kiện; tách designed, executed, passed, blocked và unresolved. Nếu không có biên có ý nghĩa, ghi lý do BVA không áp dụng.
7. Với từng T-ID, đối chiếu request API với form/flow UI thực: người dùng thường có thể gửi **đúng input và trạng thái** đó không, UI có chặn/đổi dữ liệu bằng `required`, `min`, `type`, select option, role gate hay logic client không, và có thấy kết quả trên màn hình không. Đọc source UI liên quan để lập đường thao tác, không lấy source làm evidence chạy. Nếu UI gửi chuỗi rỗng còn ca API bỏ hẳn field thì ghi là hai input khác nhau; không nhận là một lần tái hiện.

## Thực thi và evidence

Chạy mọi ca khả thi trong phạm vi khi có SUT và môi trường test phù hợp. Với feature có cả API và UI, kiểm thử API cho những input có thể gửi trực tiếp và **chuẩn bị đường manual UI cho mọi ca đi được bằng thao tác người dùng thông thường**; nếu môi trường cho phép thì chạy UI, nếu không thì để tester thực hiện sau. Browser/mobile chỉ là phương tiện chạy EP/BVA, không suy ra bộ kiểm tra layout, DOM hay UI Validation riêng. Không bắt buộc Playwright, automated test file hoặc test framework để viết hướng dẫn manual; request trực tiếp và evidence log có thể dùng cho API.

Hướng dẫn manual UI phải đủ để tester không cần đọc source hay biết API: URL/màn hình bắt đầu, tài khoản và role, fixture/trạng thái trước, từng trường và giá trị cụ thể, thứ tự click/tap, Expected nhìn thấy, vị trí/dấu hiệu Actual cần kiểm tra và screenshot nên chụp, cách reset giữa ca. Dùng cùng T-ID nếu API và UI thật sự kiểm tra cùng input/state/oracle; chỉ tách T-ID khi stimulus hoặc oracle khác đáng kể. Nếu UI chặn/biến đổi input hoặc chặn actor, ghi chính xác control/gate và giữ ca API-only; không dùng devtools như đường manual UI thông thường. Không bịa UI flow cho bug chỉ đi được qua API.

Trước khi chạy, xác định build/commit, môi trường, database và side effect. Ưu tiên instance và database cách ly; seed fixture xác định được, reset state giữa các ca khi cần. Không ghi đè database làm việc, không xóa dữ liệu người dùng và không tự dùng git restore. Nếu không thể thực thi an toàn, ghi BLOCKED với lý do cụ thể và tiếp tục phần thiết kế độc lập.

Với mỗi lần thử, ghi Run ID, T-ID, EV-ID, interface, setup, thao tác/request thật, Actual, verdict và raw evidence. API và UI của cùng T-ID có EV-ID, Actual và trạng thái riêng; không lấy PASS/FAIL API làm kết quả UI. Hướng dẫn manual suy từ source phải ghi `Dự kiến — chưa kiểm chứng UI` cho tới khi có người chạy thật. PASS/FAIL phải dựa trên chạy thật; đọc source code chỉ phục vụ thiết kế hoặc điều tra root cause. Giữ rerun như EV-ID mới và nêu run/interface được dùng để tổng hợp. Khi xong, dừng dịch vụ và xóa chỉ tài nguyên test do phiên này tạo; kiểm tra và ghi tình trạng cleanup.

## Artifact và cách viết báo cáo

Lưu trong homework/hw02/ncuong/features/<FEATURE_CODE>/, theo quy ước thư mục hiện có nếu feature được đặt alias (ví dụ Mobile). Tạo bốn file cùng evidence/:
- domain-analysis.md: rule, miền input/trạng thái, lớp EP, giá trị đại diện, Expected, rule nguồn, T-ID và coverage.
- boundary-analysis.md: từng biên, setup, giá trị/trạng thái ở các điểm có ý nghĩa, Expected, T-ID, tính khả thi và coverage.
- test-cases.md: định nghĩa ca duy nhất với setup, input/thao tác, Expected, request API nếu có, và bước manual UI cho ca UI-reachable; ghi lý do API-only cho ca không thể gửi cùng input qua UI.
- test-results.md: kết quả theo run/interface, Actual, EV-ID, verdict, coverage, bug và khoảng trống; không cộng trùng T-ID khi có cả API/UI.

Viết Domain/BVA để sinh viên review trực tiếp từ phần chính: đặt điều kiện, giá trị test, Expected và case cạnh nhau; chọn bảng hoặc đoạn ngắn theo context. Không thêm mục Đọc nhanh, lời dẫn hoặc bảng ánh xạ lặp chỉ để giải thích phần trình bày khó hiểu. Chỉ chú thích setup, precision, rule mơ hồ hoặc điểm không thể thử khi thật sự cần. Để log thô và chi tiết Actual/bug ở test-results.md và evidence/.

Cập nhật reports/main-report.md bằng số liệu và link của feature mục tiêu, giữ nguyên các feature khác. Cập nhật README.md theo tình trạng thật. Không cộng trùng case EP/BVA hoặc gán số 0 cho feature chưa làm. Quan sát ngoài EP/BVA, nếu có, lưu riêng trong supporting-materials/ và không cộng vào coverage kỹ thuật.

## Bug, phần sinh viên review và AI Audit

Điều tra một ca FAIL trước khi gọi là bug: kiểm tra oracle, fixture, tính lặp lại và evidence. Với phát hiện đã tái hiện, viết bug report có rule/T-ID, tiền điều kiện, thao tác và giá trị chính xác, Expected, Actual, severity, evidence và cách tái hiện thủ công. Phân biệt bug đã tái hiện với ứng viên còn thiếu oracle.

Sinh viên review từng bug trước. Chuẩn bị nội dung GitHub Issue theo `skills/test-findings-report-writer/assets/github-issue-template.md`: Issue phải đứng độc lập, có fixture/trạng thái ban đầu, đường tái hiện đầy đủ đã kiểm chứng, Expected/Actual, evidence và lý do đánh giá mức độ. Với bug API mà người dùng bình thường cũng có thể kích hoạt qua UI, luôn kèm **hai đường**: API đã kiểm chứng và hướng dẫn UI từng bước cho tester; nếu UI chưa chạy, ghi rõ `Dự kiến — chưa kiểm chứng UI`, không ghi Actual UI. Nếu bug đã tái hiện qua UI, ưu tiên các bước người dùng thao tác và thấy lỗi trên giao diện; API/DB bổ sung để kiểm tra trạng thái ẩn hoặc lỗ hổng backend. Nếu không thể đi cùng input qua UI, nêu gate cụ thể và giữ đường API-only. Không chép riêng khối “Reproduce nhanh” từ báo cáo. Sau khi sinh viên xác nhận, sinh viên chụp screenshot và mở GitHub Issue kèm ảnh. Đây là yêu cầu bắt buộc cho bản nộp HW02; trước bước review, ghi trạng thái Chờ người kiểm thử xác nhận, không tuyên bố đã có Issue hoặc ảnh. AI Gap Analysis và AI Critique là phần sinh viên tự đánh giá/viết; để rõ trạng thái chờ thay vì tự điền thay.

AI Audit Report là bắt buộc. Dùng ai-audit-logger/SKILL.md và template để tạo hoặc cập nhật reports/ai-audit.md từ hội thoại/transcript có thể kiểm chứng. Với mỗi tương tác, giữ tên công cụ AI, ngày giờ theo nguồn, prompt nguyên văn và output người dùng thấy; ghi thiếu dữ liệu nếu không có, không tự tạo timestamp hoặc tóm tắt thay output. Nếu file audit đã có tương tác khác, giữ lại và chỉ thêm/cập nhật phần có nguồn cho lần này.

## Kiểm tra và bàn giao

Trước khi kết thúc, kiểm tra chuỗi rule → P-ID/B-ID → T-ID → Expected → EV-ID/Actual → verdict → bug, số đếm và link. Xác nhận source/database gốc không bị sửa, hoặc nêu chính xác phần chưa xác minh. Báo cáo số ca thiết kế, đã chạy, PASS/FAIL/INCONCLUSIVE/BLOCKED/Chưa chạy, coverage theo nghĩa vụ, bug đã tái hiện, câu hỏi còn mở và trạng thái AI Audit.

Bản nộp cuối của toàn HW02 còn cần PDF cho main report, AI Audit, AI Critique; Git commit log, README có tự đánh giá và video demo; screenshot trong GitHub Issue của bug đã xác nhận. Theo dõi chúng là việc còn lại nếu chưa có, không tạo file giả hoặc nhận bài hoàn tất khi thiếu. Khi tạo commit theo yêu cầu môn học, chỉ đưa vào thay đổi thuộc bước và feature này, không gom thay đổi có sẵn của người khác.
