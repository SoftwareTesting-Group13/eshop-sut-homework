# Domain Testing Report Writer

Write clear, academically appropriate Domain Testing reports in Vietnamese.

Preserve established technical terms such as Domain Testing, equivalence class, predicate, constraint, test case, oracle, and coverage when they improve clarity.

Explain **how and why tests were derived**, not merely which tests were selected.

Write for the student who must review and defend the chosen tests. Make the **analysis rows themselves** readable: the reader should see the input/state condition, a concrete representative, its specification-based Expected result, and the linked case without decoding several other tables first. Use a note only for a genuinely non-obvious rule or exception.

Follow the user's course methodology, terminology, and notation when supplied.

## 1. Scope and responsibilities

Produce `features/<FEATURE_CODE>/domain-analysis.md`, including scope, specification analysis, and the Domain Testing method.

Focus on:

- Input domain identification.
- Constraints and predicate modeling.
- Valid, invalid, and unresolved regions.
- Equivalence class partitioning.
- Interactions between input dimensions.
- Representative test case selection.
- Traceability and domain coverage.

When Boundary Value Analysis (BVA) is required, keep it in `boundary-analysis.md` using `boundary-value-report-writer`.

Use `feature-testing-report-writer` for the overall report structure, specification analysis, shared test-case catalog, execution results, and findings.

A test case used by multiple techniques must appear only once in the shared catalog.

Do not duplicate full test definitions or execution evidence.

## 2. Required inputs

Use authoritative artifacts when available:

- Feature specification and acceptance criteria.
- Selected testing scope.
- Requirement and rule IDs.
- Input domain model.
- Input types and constraints.
- Equivalence partitions and regions.
- Decision tables or state models.
- Shared test-case catalog.
- Coverage assessment.
- Verified execution evidence.

Prefer artifacts generated by:

- `input-domain-partitioner`
- `equivalence-partitioning-generator`
- `decision-table-builder`
- `boundary-value-generator`
- `coverage-goal-planner`

Preserve existing IDs, predicates, partitions, and test-case references.

If required analysis is missing, derive it using the appropriate skill when the source specification permits.

Mark unsupported assumptions or unresolved requirements explicitly.

Never infer normative requirements from implementation behavior.

## 3. Report structure

The subsections below are a content checklist, not mandatory headings or separate tables. Combine related material when the resulting row/block is easier to review; keep separate only what adds a distinct decision or evidence claim.

Open with the feature, tested interface, source specification, and scope. Proceed to the actual rule and partition analysis; do not add a required “Đọc nhanh” or prose recap of tables.

### 3.1. Mục tiêu và phạm vi Domain Testing

Briefly identify:

- The feature or operation under test.
- Relevant requirement and rule IDs.
- Inputs, prior states, and relevant conditions.
- Why Domain Testing is appropriate.
- Which behaviors are included or excluded.

Reference the existing specification analysis.

Do not reproduce the full feature description or testing environment.

### 3.2. Xác định miền dữ liệu đầu vào

For each relevant input, document:

- Input name and meaning.
- Data type.
- Input domain.
- Units and precision when relevant.
- Nullable, optional, or required status.
- Related constraints.
- Source requirement.

Suggested table:

`ID | Đầu vào/trạng thái | Kiểu dữ liệu | Miền giá trị | Constraint | Nguồn yêu cầu`

Clearly distinguish:

- Syntactically accepted values.
- Business-valid values.
- Invalid values.
- Unspecified behavior.

Do not assume that an input is valid simply because the implementation accepts it.

### 3.3. Phân tích constraints và predicates

Translate relevant requirements into explicit logical predicates.

Put the rule in direct Vietnamese in the table or section where it is used; add a predicate only when it resolves a real precision issue. Define uncommon symbols such as `attempts'` at first use. Do not force every rule into both a prose sentence and a formula. Keep source-code observations out of this specification-derived analysis.

For each constraint:

1. Identify its source rule.
2. Express its logical condition.
3. Explain which inputs it constrains.
4. Identify dependencies between inputs.
5. Determine valid, invalid, or unknown regions.
6. Identify any contradictory or ambiguous constraints.

Consider:

- Individual field constraints.
- Cross-field relationships.
- Actor and permission conditions.
- Prior system state.
- Conditional business rules.

Use mathematical expressions when they improve precision.

Explain the meaning of each predicate in Vietnamese.

Do not invent missing equality rules, thresholds, or dependencies.

### 3.4. Phân chia equivalence classes

Partition the input domain according to specified behavioral distinctions.

For each class or region:

- Assign or reuse a stable ID.
- Define its predicate or membership condition.
- Identify valid, invalid, or unresolved status.
- Explain why it is behaviorally distinct.
- Link its source requirement.
- Record feasibility.

For multiple dimensions:

1. Identify partitions per dimension.
2. Analyze interactions and shared constraints.
3. Eliminate demonstrably infeasible combinations.
4. Preserve combinations with distinct behavior.
5. Avoid exhaustive Cartesian products without justification.

Do not merge partitions solely because they share the same broad label of valid or invalid.

Do not create separate classes without a meaningful rule-based distinction.

Suggested table, grouped by input or state dimension:

`P-ID | Điều kiện của nhóm | Giá trị/trạng thái đại diện | Expected | T-ID | Rule`

One row should be independently reviewable. State the relevant baseline in the row or immediately above a group when several rows share it. Put feasibility or unresolved-oracle notes beside the relevant row. Do not describe two classes as “equivalent” merely because both return a broad error; say which specified behavior they share. A separate mapping table is unnecessary when these columns already show the mapping.

If the class table already includes T-ID, do not add a separate class-to-test mapping table.

### 3.5. Phân tích quy tắc kết hợp (nếu cần)

Use a decision table or state-transition model only when behavior depends on interacting conditions or states.

Reference existing `DR-ID` or transition IDs.

Explain:

- Why the additional model is necessary.
- Which conditions interact.
- Which combinations are feasible.
- Which outcomes are specified.
- Which combinations remain unresolved.

Do not recreate a complete decision table if an existing referenced artifact already provides it.

Do not invent rule precedence or expected outcomes.

### 3.6. Lựa chọn representative test cases

Explain how representative cases were selected from the identified classes or regions.

For every selected case:

1. Identify the source rule.
2. Identify the target class or region.
3. Explain why its input represents that class.
4. Keep unrelated inputs at feasible baselines where possible.
5. Ensure other invalid conditions do not mask the target behavior.
6. Link the existing stable `T-ID`.
7. Reference its specification-based oracle.

Use boundary values when appropriate, but leave detailed ON/IN/OUT derivation to the BVA section.

A single test case may support multiple equivalence classes or testing techniques when the coverage claim is justified.

Keep full setup, input, actions, expected results, and actual results in the shared `test-case-catalog`.

### 3.7. Đánh giá coverage và giới hạn

Use coverage obligations and metrics from `coverage-goal-planner` when available.

Report:

- Total identified classes or regions.
- Feasible obligations in scope.
- Obligations covered by designed tests.
- Obligations supported by execution evidence.
- Uncovered obligations.
- Infeasible, excluded, or unresolved regions.
- Relevant residual risks.

Define the denominator before reporting percentages.

Distinguish:

- Designed coverage.
- Executed coverage.
- Passed coverage.

Never treat a designed test as evidence of successful execution.

Do not recalculate coverage independently when an authoritative coverage assessment already exists.

Do not claim complete Domain Testing coverage if feasible obligations remain uncovered.

### 3.8. Kết quả thực thi (nếu có)

Briefly summarize execution outcomes using verified evidence.

Reference the shared test-case catalog for:

- Actual results.
- PASS/FAIL/BLOCKED status.
- Logs or screenshots.
- Test execution records.
- Related defect IDs.

If tests have not been executed, explicitly state `Chưa chạy`.

If the specification does not establish an oracle, state `Chưa xác định theo đặc tả`.

Do not fabricate observations or present assumptions as confirmed results.

Avoid duplicating detailed execution tables.

## 4. Writing guidelines

Write in formal, concise, and understandable Vietnamese suitable for a university Software Testing report.

Follow this analytical sequence:

**Requirement → Input Domain → Constraints → Equivalence Classes → Representative Tests → Coverage**

Each analytical subsection should expose the chosen condition, concrete representative, Expected, source rule, and test link as directly as its context permits. Explain derivation only when a reviewer cannot infer it from the rule and values.

Use concrete feature-specific explanations.

- Make headings and column names say what the reader is looking at. Define `R-ID`, `P-ID`, `C-ID`, `T-ID`, and feature-specific symbols only where their meaning is not evident from the column or first row.
- Keep the main line of reasoning in the order **rule → behavior groups → representative case**. Put the concrete value and Expected beside the group, not in a distant mapping table. Add a state/decision model only when it resolves a testing decision that the class table cannot show.
- Remove a table or paragraph if it repeats the same mapping without adding a rule, setup, oracle, limitation, or coverage fact. Do not add a mandatory introduction, reading guide, worked example, or summary simply to make dense tables seem easier.
- Keep analysis about requirements and chosen tests here. Put detailed Actual, verdicts, code-level diagnosis, and raw evidence in `test-results.md`; use a brief link if the observation changes how a coverage claim must be worded.
- If reporting coverage, say in words what the numerator and denominator count. Separate “có case”, “đã chạy”, and “đã đạt”; never present a percentage without its counted obligations and unresolved exclusions.

Avoid generic textbook paragraphs that could apply unchanged to any feature.

Use tables for structured mappings and short paragraphs for reasoning.

Define IDs and unfamiliar notation at first use.

Adapt section numbering to the surrounding report.

## 5. Evidence and traceability

Maintain the relationship:

`Requirement/Rule → Predicate → Class/Region → T-ID → Oracle → Evidence`

Preserve stable identifiers across Domain Testing, BVA, decision tables, coverage reports, and the shared test-case catalog.

If source artifacts conflict:

1. Identify the conflicting information.
2. Record the affected requirements or tests.
3. Avoid silently choosing a preferred result.
4. Mark affected conclusions as unresolved until reconciled.

Implementation behavior may be reported as an observation but must not replace the specification-based oracle.

## 6. Quality gates

Before finalizing, verify:

- Every scoped requirement is modeled or explicitly excluded.
- Input domains and types are documented.
- Constraints are traceable to source rules.
- Cross-field dependencies are considered.
- Valid, invalid, and unresolved regions are distinguished.
- Equivalence classes have justified distinctions.
- Infeasible combinations are not presented as executable.
- Every claimed covered class links to a real test case.
- Representative values are justified.
- Unrelated invalid inputs do not mask the target behavior.
- Expected behavior follows the specification.
- Test IDs match the shared catalog.
- Coverage denominators and metrics are consistent.
- Designed and executed coverage are separated.
- Execution claims have verifiable evidence.
- Domain Testing and BVA are reported separately when BVA is required; if evaluated but inapplicable, explain why no boundary cases were generated.
- No complete test-case catalog is duplicated.
- The derivation process is reproducible from the report.
- A reader can identify a representative class, its concrete test value, Expected, source rule, and case directly from the relevant row or compact section.

## Constraints

- Do not invent requirements or expected behavior.
- Do not infer specifications from SUT behavior.
- Do not silently resolve ambiguous predicates.
- Do not fabricate test execution results.
- Do not claim uncovered or infeasible regions are covered.
- Do not duplicate test cases across method sections.
- Do not introduce unnecessary Cartesian combinations.
- Do not equate Domain Testing coverage with complete product correctness.
- Prefer precise, traceable reasoning over lengthy generic explanations.
