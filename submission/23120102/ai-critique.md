# AI Critique (200–300 words)

AI helped turn four functional requirements into a broad interface checklist quickly, but the initial analysis was incomplete in ways that matter for this application. A generic checklist can make a screen look thoroughly covered while missing business-specific edge conditions: the coupon’s inclusive minimum-spend boundary, per-user usage cap, the definition of delivered-only revenue, and terminal order states. These details had to be traced back to the SRS and source rather than accepted from a generic usability pattern. Static code review also risks overstating a defect: an incorrect-looking calculation in source is a strong lead, but the running UI, API response, and data fixture still need to confirm what a user sees.

The AI cannot recruit participants, obtain consent, observe genuine hesitation, or produce authentic cross-platform screenshots. It would be easy to generate plausible names, SUS scores, or screenshots, but doing so would turn evidence into fiction and violate the assignment’s explicit constraints. This report therefore separates test design and source-review hypotheses from work that has not happened. AI-generated checks can also overemphasize technical accessibility and error states while underrepresenting the language, expectations, and trust concerns of Vietnamese shoppers; real sessions are needed to expose those gaps.

I learned to use AI as a structured drafting and review partner, not as an authority or substitute participant. Each suggestion should be tied to a requirement, translated into an observable test, and checked against the live product. Human review should challenge coverage, verify arithmetic and state rules, and preserve provenance. AI is most useful when it makes assumptions visible and leaves an auditable path from requirement to evidence; unsupported certainty is a warning sign, not a finished result.
