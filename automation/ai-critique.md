# AI Critique - draft for student review

AI helped translate three functional requirements into browser cases and a reusable Playwright structure. It organized the work, but the first output contained mistakes that would have weakened the evidence if accepted without review: for FR-04, the initial test logic expected an empty phone value to submit despite the valid-format rule; for FR-09, a substring locator matched multiple amounts; and for FR-15, selecting a nonexistent category did not model an empty category list and could stall the test. I corrected these after comparing fixtures and assertions with the SRS and rendered application. The execution also exposed behavior generic generation could not safely assume: the profile form rejects valid numbers beginning with the required zero and accepts some numbers beginning with one; the admin product form submits values the SRS says must be rejected; and the edit-isolation test failed in Chromium and WebKit but passed in Firefox. These outcomes need human classification because automation defects and SUT defects both appear as failed assertions. The AI missed issues because its first pass favored broad coverage and plausible selectors over checking every business rule against source and browser behavior. I learned to use AI as a drafting partner, then validate every expected result, locator, and failure against both the specification and observed behavior. A passing report is meaningful only when the test is sound, and a failing report is a lead until its cause is confirmed. The API mocks improve repeatability but limit conclusions to UI behavior; live backend tests with resettable data are still needed before claiming full feature coverage.

> Drafted with AI assistance. The student must review the analysis and personalize it with their own observations before submission.
